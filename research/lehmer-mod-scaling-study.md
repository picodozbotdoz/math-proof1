# Lehmer scaling study: past 512 without 71 GB

**Status: study + kernel benchmarks complete, 2026-10-24.**  Question: the
kernel-verified nonvanishing bound `τ n ≠ 0` for `n ≤ 512`
(`MathProof/Tau/LehmerMod.lean`, `decide +kernel` on mod-`P` list arithmetic)
dies at `d = 1024` with a kernel heap `> 71 GB` on a 32 GiB container.  Can the
program be improved to reach 4096 and beyond — under the project's standing
constraint **no `native_decide`, no external CAS, kernel evaluation only**?

**Answer: yes.**  Packed-bignum arithmetic — one GMP-backed `Nat` per
coefficient list in base `2^80`, one `Nat.mul` per dense convolution —
verified **1024, 4096 and 16384 in 174 s** of kernel time in benchmark form
(`Bench/Packed/BBenchPacked.lean`), and the balanced refinement
(`BBenchPackedBal.lean`) **verified 16384 and 65536 in 662 s**, peaking at
60 GiB (needs a > 64 GiB machine; on the current 32 GiB budget the safe landable
bound is **16384**, a 32× improvement).  The entry data is generated by
`tools/gen_packed_bench.py`, cross-checked against the 21 kernel-verified τ
values of `Basic.lean`; the τ residues mod `P = 999999937` are nonzero
throughout `n ≤ 65536`.  Turning the benchmark into a theorem needs elementary
packing lemmas + Mathlib's pentagonal number theorem — no new mathematics.

All measurements come from the new Modal build telemetry (§7):
2 CPU / 32 GiB-request containers, `lean_check.py` per-module runs.

## 1. What actually fails, with numbers

| computation | result | peak tree RSS | kernel wall | failure mode |
|---|---|---|---|---|
| current list arith, **512** (builds `Lehmer` too) | ✔ `tau_ne_zero_of_le_512` | **24.1 GiB** | 186 s module (270 s lake wall) | none — but 75 % of budget |
| current list arith, **768** (`BBenchScale.lean`) | ✘ | > 39.5 GiB | > 363 s | `(kernel) deterministic timeout` while climbing |
| forced list arith, **1024** (`BBenchList.lean`) | ✘ | > 34.6 GiB | > 305 s | `(kernel) deterministic timeout` while climbing |
| current list arith, 1024 (previous iteration) | ✘ | > 71 GB | — | heap (preempted) |
| packed v1, **1024 + 4096 + 16384** (`BBenchPacked.lean`) | ✔ all three | **41.3 GiB** cumulative | **174 s** | none (over the soft memory request — see §7) |
| packed v2 balanced, **16384 + 65536** (`BBenchPackedBal.lean`) | ✔ both | **60.1 GiB** (65536 decide alone ≈ +42 GiB over an 18 GiB plateau) | **662 s** | none (needs > 64 GiB) |

Two distinct ceilings interlock to kill the naive approach, and a third guard
bounds any fix:

1. **Retention (memory).**  The kernel evaluator is lazy and does **not force
   function arguments**: every accumulator step conses a new suspension, and
   the whole suspension DAG of a `decide` stays live until the declaration
   completes.  This was verified directly with a constant-live-set probe
   (`BBenchBurn.lean`): a nested loop with O(1) live data ramped RSS linearly
   to 9.3 GiB over ~2M small-Nat steps (~0.6–4 KB retained per reduction step,
   algorithm-independent), and RSS *dropped back to 4.5 GiB* the moment the
   declaration died — memory is released at declaration boundaries, never
   during evaluation.  So **peak RSS ≈ (bytes-per-step) × (total kernel
   reduction steps of the longest single declaration)**; the list arithmetic
   of `LehmerMod` needs Θ(d²) steps with list-cell suspensions (~90 KB/step²
   effective), which is the 24 GiB @ 512 / 71 GB @ 1024 curve.
2. **Deterministic kernel time.**  The kernel checks each declaration against
   a heartbeat budget: `addDeclCore env maxHeartbeats maxRecDepth`, default
   `maxHeartbeats = 200000` (Lean core, `Lean/CoreM.lean`; failure message
   `(kernel) deterministic timeout`).  200000 heartbeats ≈ 200 s of this
   workload — the 512 decide (~150–186 s) fits, 768/1024 do not.  **Any
   multi-minute `decide +kernel` needs `set_option maxHeartbeats <large>`**;
   none of the project's files lift it today.
3. **Deep recursion guard.**  `(kernel) deep recursion detected` caps the
   *depth* of recursor unfolding / thunk forcing (`maxRecDepth`; also hit when
   forcing a multi-million-deep suspension chain, per the burn probe).  Any
   fix must keep both depth and total steps small — the packed scheme does.

## 2. Assessment of the external commentary (`external-doc/Lehmer-ds-comment-1024.md`)

| Suggestion | Verdict (measured where possible) |
|---|---|
| `native_decide` for large `d` | **Rejected by project rules** (AGENTS.md: kernel-only). Also unnecessary — the packed scheme gets the memory/time win while staying kernel-only. |
| Truncate `psubM`/`pmulM` to `d` each step | Marginal: `PbuildM` already truncates (`List.take d`); intermediate lengths exceed `d` by at most the shift. The heap is retained *suspensions*, not over-long tails. |
| Tail-recursive `PbuildM` via `foldl` | Does not address the failure: the kernel is lazy, so tail form does not force anything; an accumulator passed unforced *builds* a suspension chain (burn probe, §1). Measured: strict *forcing* — §3 — is what actually helps, and even it is not enough. |
| `UInt64`/`BitVec` coefficients | Wrong diagnosis: the kernel's fast binary-op path covers GMP-backed `Nat` (`add/sub/mul/div/mod/shifts/beq/ble/…`); there is no such path for `BitVec`/`UInt64`, and all values here already fit one GMP limb. The cost driver is per-step suspension retention, not integer representation. |
| `hex-poly-fast` / NTT library | External dependency, and moot: once each convolution is a single GMP `Nat.mul` (§4) the schoolbook constant is irrelevant at these sizes. |
| Reflected certificate | Right instinct (the research log pointed there too) — but the concrete scheme must be chosen carefully: see §5 for why *point-evaluation* certificates are unsound here, and §4 for the correct reflection (convolution checking via bignums). |

## 3. Quick win tested: strict forcing (zero new mathematics) — not enough

A `forceN` gate after each `Pbuild` step and each of the five `pmulM`s forces
every element to a literal
(`List.all` chains `Bool.and`, and `Nat.ble` is a kernel binary operation, so
whnf-ing the `if` descends into every element):

```lean
private def forceN (l : List ℕ) : List ℕ :=
  if l.all (fun x => Nat.ble (x % P) (P - 1)) then l else l
```

Measured (`BBenchList.lean`): forcing demonstrably helps *relatively* — the
forced 1024 run burned 305 s / 34.6 GiB before the timeout, i.e. it got further
than the unforced 768 run (363 s / 39.5 GiB) on a 4/3× larger computation —
but it still exceeds both ceilings.  Element-level forcing cannot fix the
retention because the dominating suspensions are the *arguments threaded
through the recursions themselves* (and the below-spines), not just dangling
element thunks.  Conclusion: **the list representation is exhausted; the fix
must change the data representation to minimize total kernel reduction steps.**
(`forceN l = l` is provable by `split <;> rfl`, so this pattern remains a free
small win if ever needed.)

## 4. The fix: packed-bignum kernel arithmetic

Represent a coefficient list (entries `< P`) as **one natural number in base
`2^80`**: `packAsc [c₀, c₁, …] = c₀ + 2^80·(c₁ + 2^80·(…))`.  Then:

* **dense truncated multiplication = one `Nat.mul`.**  The kernel evaluates
  `Nat.mul` on GMP literals at C speed, so the Θ(d²)-multiplication
  convolution stops being Θ(d²) *kernel reduction steps*; slot width 80 keeps
  raw convolution digits `< d·(P−1)² < 2^76` (d ≤ 2^16) from bleeding between
  slots, and digit extraction (`N % 2^80`, `N / 2^80`, `% P`) is O(d) kernel
  big-operations per multiplication.  The 24th power is five such products
  (`24 = 16 + 8`).
* **the ∏(1 − X^m) phase is free**: by Euler's pentagonal number theorem the
  η coefficients are ±1 at generalized pentagonal indices, 0 elsewhere, and
  Mathlib has exactly this, coefficient-wise over power series
  (`Mathlib/Combinatorics/Enumerative/Pentagonal/PowerSeries.lean`:
  `coeff_prod_one_sub_X_pow_eventually_eq`, `coeff_pentagonalSeries_pentagonal`),
  so the entry list can be built structurally and certified without the
  d-step `PbuildM` loop at all.

**v1 measured** (`BBenchPacked.lean`, linear pack/unpack): all of 1024, 4096,
16384 verified in one module, 174 s kernel time, peak 41.3 GiB rising linearly
throughout (per §1's law: the linear `packAsc`/`digitsModP` walks retain
Θ(d) suspensions *of growing big values* — Θ(40·d²) bits per walk).

**v2 balanced** (`BBenchPackedBal.lean`): split the list / digit range at the
midpoint instead of walking linearly (fuel-structural recursion, depth
`log₂ d`, combine with one shift-mul-add / mask+div).  Isolated probe
(`BBenchPack.lean`, one decide per theorem): `packAsc@16384` = 3.4 GiB ramp
vs `packBal@16384` = **1.0 GiB** — the tree removes ~3.4× of the packing
retention.  Full pipeline: **16384 + 65536 both verified in 662 s**, with the
RSS curve plateauing at ~18 GiB right after the 16384 decide (memory *is*
reused across declarations) and the 65536 decide adding ~42 GiB on top —
60.1 GiB peak.  On the 32 GiB budget the landable bound is therefore
**16384** (comfortably, single-decide ≈ 16–18 GiB); 65536 is *demonstrated
kernel-verifiable* but needs a > 64 GiB machine (or further constant shaving:
sparse η-packing, wider slots to skip reductions).

Slot arithmetic stays safe to `d = 2^16` at width 80 (`d·(P−1)² < 2^76`);
beyond that, widen the slot (e.g. 96 bits, `d ≤ 2^22`) — a parameter change
in the generator and in the proofs' digit-bound lemma.

## 5. Why point-evaluation certificates do NOT work (analysis)

The tempting scheme — verify `cert ≡ ∏(1−X^m)^24 (mod X^d)` by evaluating both
sides at `d` distinct points and applying Mathlib's
`Polynomial.eq_of_natDegree_lt_card_of_eval_eq'` — is **unsound in this
shape**: `∏(1−a^m)^24` evaluates the *untruncated* product, and evaluating a
power series at a point aliases coefficients `f_i, f_{i+d}, f_{i+2d}, …`
(wrap-around).  The check would certify `cert_i = Σ_k f_{i+kd}`, not
`cert_i = f_i` — residues could cancel across congruence classes and a
vanishing τ would slip through.  There is no cheap way to evaluate a
*truncated* series at a point without already knowing its coefficients, and
the only ring hom `F[X]/(X^d) → F` over a field is evaluation at 0.  So any
"evaluate at points" certificate must be rejected: **convolution checking
(§4) is the correct reflection principle** — it verifies exactly the
truncated coefficient identity.

## 6. Recommended next iteration

1. New module `MathProof/Tau/LehmerPacked.lean`; target statement
   `theorem tau_ne_zero_of_le_16384 {n} (h1 : 1 ≤ n) (h2 : n ≤ 16384) : tau n ≠ 0`
   (residues are nonzero through 65536, so the bound can ratchet later — on
   bigger Modal memory or after constant shaving; 65536 is already proven
   *feasible* by `BBenchPackedBal.lean`).  Keep the module out of CI exactly
   as `LehmerMod` is (GitHub runners have ~7 GB; the decide needs ~16–18 GiB
   and ~2 min).
2. Soundness work — all elementary, no analysis:
   * *Packing lemmas*: "digits of `pack a * pack b` are the convolutions
     `Σ aᵢbⱼ` (`i+j=k`), given entries `< P` and the slot bound" (induction +
     `Nat.divAddMod`-style algebra + `omega` for bounds); `packBal`/`digitsBal`
     correctness by induction on fuel; round-trip on residues.  Transport
     into `ZMod P` mirroring `L2PMod` in `LehmerMod.lean`.
   * *η entry list*: build generalized pentagonal indices structurally,
     certify via Mathlib's pentagonal number theorem (the power-series
     statement is coefficient-wise → truncation bookkeeping only).  This
     replaces `PbuildM` entirely.
   * *Primality instance* `Fact (Nat.Prime 999999937)` if the transport needs
     the `ZMod P` field (`norm_num [Nat.prime_decider]`; one-time cost).
   * *Nonvanishing transport*: `tauOf_ne_zero_of_mod` pattern applies
     verbatim — a nonzero residue mod `P` certifies `tauOf i ≠ 0`.
   * Include `set_option maxHeartbeats …` / `maxRecDepth …` as in the
     benches (§1, ceilings 2–3).
3. Keep `LehmerMod.lean` (512) as the fast smoke check; the packed module
   becomes the record holder.  `#print axioms` audit expected: `propext` only.
4. Beyond 16384: widen slots (digit-bound lemma is parametric), pack η
   sparsely (only ~2√(2d/3) nonzero entries), and only then ask for more RAM;
   GMP's multiplication asymptotics do the rest.  10^5–10^6 is an engineering
   question, not a mathematical one.

Trust story for the certificate data: the η entry list is unverified *data*;
every mathematical claim is still kernel-checked (a wrong list makes the
`decide` fail, never pass — the probe bug in §7's `BBenchPack` history was
caught exactly this way).  This is the same trust profile as any proof by
`decide`: the computation, not the mathematician, carries the proof.  The
generator (`tools/gen_packed_bench.py`) is deterministic, dependency-free
numpy, self-checked against the 21 kernel-verified τ values.

## 7. Modal build telemetry (this study's infrastructure)

`lean_check.py` / `lean_build.py` now wrap `lake build` with a std-lib-only
process-tree sampler (1 Hz `/proc` walk): live `[telemetry]` milestone lines on
every ≥10 % peak-RSS growth, and a final summary —
`wall / peak_tree_rss / CPU / children ru_maxrss` — plus a decimated RSS
curve.  Milestones stream as they happen, so they survive OOM kills.  No Modal
resources were added or changed; image definitions are untouched (layer cache
shared as before).  This telemetry produced every number in this study —
including the failure curves (the 768/1024 climbs to 39.5/34.6 GiB before the
kernel timeout, and the 9.33 → 4.45 GiB release at declaration death in the
burn probe).

Operational discoveries recorded for future runs:

* `--file X.lean` now also *builds* module `X` (it previously only overlaid
  the file and silently built the default target — the trap that initially
  swallowed the first bench round).
* Modal `memory=` is a soft request: a "32 GiB" container was observed
  running at 60 GiB RSS.  Budget conclusions here use the measurements, not
  the nominal cap.
* Kernel guards to respect in any large computation: `maxHeartbeats`
  (deterministic time, default 200000 ≈ 200 s), `maxRecDepth` (unfolding
  depth AND suspension-chain forcing depth).
