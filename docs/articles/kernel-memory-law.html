27 GiB per million operations: the memory law of kernel computation

The kernel keeps everything until a declaration ends. Once that was measured, the heaviest module dropped from 202 GiB to 13.5 GiB without changing the mathematics.

WHAT WAS MEASURED

Peak memory of kernel decide grows linearly with the work done inside one declaration: about 27 GiB per million Poly5 list operations in this code. Memory is released only when the declaration ends. These are measurements on one project, not theorems, and the constant depends on the data representation.

In Iteration 18, one Lean file needed 202 GiB of memory to compile. The obvious suspects were simp and ring, and the project's improvement notes said so. Profiling each declaration showed that was wrong. e3dec, a single kernel decision, accounted for 18.5 GiB of a 24.5 GiB peak, while the surrounding simp lemmas added nothing measurable.

Why the kernel behaves this way

An earlier probe had already found the mechanism. A nested loop with constant live data ramped memory steadily to 9.3 GiB, and memory fell back to 4.5 GiB the moment the declaration died. The kernel evaluator is lazy and keeps intermediate terms in caches for the whole declaration. So a program with almost no live data can still use a lot of memory: what counts is how many steps it took.

The model also solved a puzzle: why was e4 heavier than e6? Because e4 was computed as 15 separate products, while e6 is a single product. Time follows a similar line, around 300 s per million operations.

Two levers

  1. Do less work. Elementary symmetric functions were computed by brute force as C(6,k) products. The recurrence Ej,k = Ej−1,k + Θj·Ej−1,k−1 cut the e4 left side from 7.16 M to 0.44 M operations.
  2. Reset the caches. Split one huge decision into several, each proving step = literal. Each literal becomes a checkpoint, and the next declaration starts clean. The generator places a checkpoint at about 0.5 M modelled operations.

The mathematics and the theorems above the chain did not change.

The full chain went from about 2 hours to about 33 minutes. Going further has limits: a prototype with one declaration per operation gave 10.2 GiB against 24.5 GiB on e3 but doubled the time, because large literals cost time to elaborate. The coarse split was the better trade.

A rule of thumb you can use

Before writing a kernel certificate, estimate the reduction steps in the largest single declaration, and calibrate a bytes-per-step constant on a small case. If the projection is too high, split at literal checkpoints or change the representation. Do not start by asking for more memory.

The constant depends heavily on the representation. Raw kernel steps cost about 0.6 to 4 KB each, while one Poly5 list operation costs about 27 KB because it unfolds many instances on nested pairs.

WHERE THE TRICK STOPS

Checkpoints work when intermediate results are small. For packed bignums, an intermediate at d = 131072 is one 10.5-megabit number, so a checkpoint still puts it all in one declaration. That is partly why the project declined to push past 65,536: the split would have to be at digit-list level, which has not been tested.
