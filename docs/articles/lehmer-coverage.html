New exact count

99.9093%: what is actually proved about τ(n) ≠ 0 below 2³²

Three proof routes combine into one theorem. Counted exactly, it reaches all but 3,894,333 of the 4,294,967,295 positive integers below 2³², and the gap has a precise shape.

WHAT IS PROVED

τ n ≠ 0 for every n ≥ 1 whose prime factors are each at most 65,536 or not congruent to −1 mod 691, with no bound on n and any exponents. This is a Lean theorem. The count of 4,291,072,962 below 2³² is an exact computation with a kernel-verified count only at the anchors 2¹⁸ and 2²⁰.

Lehmer asked in 1947 whether the Ramanujan function τ(n), defined by q ∏m≥1(1 − qm)24 = Σ τ(n) qn, ever vanishes. It is still open. Over many iterations this project built several separate routes to nonvanishing, and the natural summary was vague: "almost all 32-bit indices". This article replaces that phrase with an exact count.

Three routes, one theorem

The Lean statement below is the fusion. It reads almost like a plain sentence:

theorem tau_ne_zero_of_prime_factors_le_65536_or_mod {n : ℕ} (hn : 0 < n)
    (h : ∀ p : ℕ, p.Prime → p ∣ n → p ≤ 65536 ∨ p % 691 ≠ 690) : tau n ≠ 0
  • Dense computation. Lean's kernel checks τ(n) ≠ 0 for all n ≤ 65536 by evaluating the coefficients modulo a prime (how that fits in a kernel).
  • The 691 sieve. Ramanujan's congruence gives τ(n) ≡ σ₁₁(n) (mod 691), so 691 ∤ σ₁₁(n) forces τ(n) ≠ 0. For a prime, 691 ∣ 1 + p¹¹ happens only when p ≡ −1 (mod 691), so every other prime of any size is settled by one residue test.
  • Multiplicativity and Lehmer's lemma. Mordell's theorem combines coprime factors, and Lehmer's reduction removes exponents. Only primes matter.

So a prime is out of reach only if it is bad: larger than 65,536 and congruent to −1 mod 691. The smallest bad prime is 70,481, and that gives the second headline theorem, tau_ne_zero_of_lt_70481: τ(n) ≠ 0 for every 0 < n < 70481, past the dense bound with no extra computation.

The counting trick

Counting integers with a bad prime factor usually needs inclusion-exclusion. Here it does not, because of one inequality:

70481² = 4,967,571,361 > 2³²

Every n < 2³² therefore has at most one bad prime factor, to the first power. The multiples of different bad primes never overlap, and the uncovered count is a plain sum:

U(B) = Σbad p < B ⌊(B − 1) / p⌋   for all B ≤ 2³²

The gap is spread thinly. The prime 70,481 alone accounts for 60,937 uncovered integers, the first five bad primes for 5.9%, and the first thousand for 53%. The last bad prime below 2³² is 4,294,967,161.

Why the next doubling was refused

Raising the dense bound to 131,072 was the obvious next move, and the project declined it on evidence. It would remove exactly five bad primes (70481, 92593, 96739, 105031, 120233), add 0.0053 percentage points of coverage below 2³², and extend the initial segment to 134,053. The projected cost is 110 to 125 GiB of kernel memory for one declaration. The exact census made that trade visible, since the remaining gap sits in 294,613 larger primes that no dense computation near this scale can reach.

In context

READ THIS AS A STATEMENT ABOUT PROOF, NOT ABOUT THE RECORD

Ordinary computations go far beyond this. Derickx, van Hoeij and Zeng report τ(n) ≠ 0 for all n below about 8.16·10²³ (arXiv:1312.6819; the bound is as cited by Bennett et al., 2022). Nobody suspects the 3,894,333 "uncovered" integers. They are simply the ones this particular Lean theorem does not reach. The new thing here is a precise account of what a proof checker has confirmed.

How the numbers were checked

The study script is committed with its data. For this article the census was recomputed from scratch by a separate sieve, which reproduced the 294,618 primes byte for byte and every row of the table. In Lean, uncovered_2p18 and uncovered_2p20 prove the counts 23 and 227 in the kernel, with the no-overlap identity proved structurally as card_uncoveredSet. The full 2³² count remains an exact Python computation, not a Lean theorem.
